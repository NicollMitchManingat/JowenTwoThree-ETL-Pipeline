# Stage 1: Data Extraction Documentation — Jowen Two Three ETL Pipeline

## 1. Data Source and Extraction Specification

### 1.1 Source System

The source system is the **Jowen Two Three web application**, an integrated Point-of-Sale (POS), Inventory Management, and Customer Traffic Recording System developed for Jowen's Kitchen & Cafe. Its purpose is to record and manage business transactions, inventory activities, and customer traffic.

The system generates operational records that can be used to monitor sales performance, inventory availability, customer traffic, and overall business performance. These records serve as the primary source of data for the proposed Extract, Transform, and Load (ETL) pipeline.

### 1.2 Source Database or File

The source database is **Supabase PostgreSQL**, which stores the operational records generated by the Jowen Two Three web application.

| Specification | Description |
|---------------|-------------|
| Source database | Jowen Two Three operational database |
| Database platform | Supabase PostgreSQL |
| Database management system | PostgreSQL |
| Data format | Structured relational data stored in database tables |
| Data categories | Sales transactions, inventory activities, and customer traffic records |
| Extraction access | Python database connection |

The extraction process retrieves the required records directly from the source PostgreSQL database. No external CSV, JSON, or Excel files are required for the proposed extraction process because the operational data is stored in the database.

### 1.3 Extraction Method

The pipeline uses **Python-based batch extraction** to retrieve operational records from the Jowen Two Three source database. Python connects to the source PostgreSQL database, executes the required queries, and extracts the records needed for business reporting and analytics.

The extracted data will be prepared for the succeeding data cleaning and transformation stages.

**Extraction Specification:**

| Specification | Description |
|---------------|-------------|
| Extraction tool | Python |
| Source connection | Supabase PostgreSQL |
| Extraction type | Batch extraction |
| Extraction mode | Incremental extraction is proposed for routine daily processing, subject to the availability of a reliable date or timestamp field |
| Extraction window | Previous business day's records |
| Extraction schedule | Daily, after business operations have been completed |
| Extraction process | Connect to the source database, execute queries, retrieve the required records, and prepare the extracted data for validation and transformation |

For incremental extraction, the pipeline should use an appropriate date or timestamp field, such as the transaction date for sales records, to identify records within the extraction window. The actual field names must be verified against the source database schema before implementation.

The extraction window will cover records from the previous business day. The pipeline must apply consistent date boundaries to ensure that records are retrieved from the intended period.

If a reliable date or timestamp field is unavailable, or if the source database does not support dependable incremental extraction, a full extraction of the required tables may be considered until an appropriate incremental extraction method is established.

### 1.4 Extraction Scope

The extraction scope covers the operational records needed to generate daily, weekly, and monthly business reports. The selected records will be used to produce summarized information for the separate PostgreSQL data warehouse.

The following data categories are included:

| Data Category | Description | Intended Use |
|---------------|-------------|--------------|
| Sales transactions | Records of sales and customer orders | Calculate total sales and the number of orders |
| Inventory activities | Records related to inventory items and stock availability | Determine total inventory items, low-stock items, and out-of-stock items |
| Customer traffic | Records of customer entries and recorded traffic activity | Calculate total customer entries and identify peak customer-entry periods |

The extraction will retrieve the relevant records from the source database tables containing sales transactions, inventory information, and customer traffic data.

For routine daily extraction, the pipeline will prioritize records associated with the previous business day. Historical records may also be extracted during the initial warehouse setup, depending on their availability and the agreed reporting requirements.

### 1.5 Source Limitations and Assumptions

The following limitations and assumptions may affect the extraction process:

**Limitations:**

1. **Database availability:** The extraction process depends on the availability of the Supabase PostgreSQL source database. Connection failures may prevent the pipeline from retrieving the required records.
2. **Database access permissions:** The Python extraction script must have the appropriate database credentials and read permissions to access the required source tables.
3. **Schema changes:** Changes to table names, column names, or data types may cause extraction queries to fail or retrieve incomplete data.
4. **Data completeness:** Missing, incomplete, or incorrectly recorded operational data may affect the accuracy of the extracted dataset.
5. **Historical data availability:** The availability of historical records depends on the records retained in the source database.
6. **Incremental extraction requirements:** Incremental extraction depends on the availability of a reliable date or timestamp field and a consistent method for identifying records within the extraction window.

**Assumptions:**

1. The Jowen Two Three web application stores sales transactions, inventory activities, and customer traffic records in the Supabase PostgreSQL database.
2. The required operational records are available before the scheduled daily extraction begins.
3. Database connection settings and credentials are configured securely through environment variables or secure configuration files.
4. The pipeline runs daily after business operations have been completed.
5. The relevant source tables and their actual column names will be verified before the extraction script is implemented.
6. A suitable date or timestamp field will be identified if incremental extraction is used.
7. Extracted records will be checked for completeness and traceability before proceeding to the next stage of the ETL pipeline.

These limitations and assumptions will guide the implementation of the extraction process and help ensure that the retrieved data is suitable for the succeeding cleaning, transformation, and loading stages.

## 3. Extraction Validation and Data Quality Checks

The Jowen Two Three Batch ETL Pipeline uses Python to extract operational data from the Supabase PostgreSQL database. Before the extracted data proceeds to the transformation stage, validation checks must be performed to verify database accessibility, source structure, record identification, extraction completeness, and successful execution.

### 3.1 Source Connection and Accessibility

- **Check Name:** Source connection and accessibility
- **Target:** Jowen Two Three operational database hosted on Supabase PostgreSQL.
- **Purpose:** To verify that the Python extraction process can establish a database connection and access the source records required by the pipeline.
- **Validation Criteria:**
  - **Pass:** The database connection is established successfully, and the configured connection can access the required source data.
  - **Fail:** The connection cannot be established, authentication fails, or the required source data cannot be accessed.

### 3.2 Required Tables and Columns Exist

- **Check Name:** Required Tables and Columns Existence
- **Target:** Source tables and columns required to extract sales transactions, inventory activities, and customer traffic records.
- **Purpose:** To ensure that all database objects referenced by the extraction process exist and are accessible before the extraction queries are executed.
- **Validation Criteria:**
  - **Pass:** All configured source tables and required columns exist and are accessible.
  - **Fail:** A required table or column is missing, renamed, or inaccessible.

### 3.3 Required Identifiers are Present

- **Check Name:** Required Identifier Completeness
- **Target:** Primary key or unique identifier columns in the extracted source records.
- **Purpose:** To ensure that each extracted record contains the identifier needed to identify and trace the record back to its source.
- **Validation Criteria:**
  - **Pass:** All extracted records contain non-null values in the required identifier columns.
  - **Fail:** One or more extracted records contain a null value in a required identifier column.

### 3.4 Primary Key Uniqueness, where Applicable

- **Check Name:** Primary Key Uniqueness
- **Target:** Primary key columns or designated unique identifiers in the extracted source tables.
- **Purpose:** To verify that the extracted results do not contain multiple records with the same primary key value, which could indicate an extraction or query issue.
- **Validation Criteria:**
  - **Pass:** Every primary key value is unique within the corresponding extracted result.
  - **Fail:** Duplicate primary key values are detected within the extracted result.

### 3.5 Record Count Validation

- **Check Name:** Record Count Validation
- **Target:** Extracted sales, inventory, and customer traffic records for the configured extraction period.
- **Purpose:** To determine whether the extraction process retrieves the expected number of eligible source records.
- **Validation Criteria:**
  - **Pass:** The extracted record count equals the count of eligible source records retrieved or counted using the same extraction window and query conditions.
  - **Fail:** The extracted record count differs from the expected source record count without an identified and documented explanation.

### 3.6 Extraction Completeness

- **Check Name:** Extraction Completeness
- **Target:** The extracted dataset for the scheduled batch processing period.
- **Purpose:** To confirm that all eligible records within the defined extraction window have been retrieved from the source database.
- **Validation Criteria:**
  - **Pass:** All eligible source records within the configured extraction window are present in the extracted dataset.
  - **Fail:** One or more eligible source records are missing from the extracted dataset.

### 3.7 Extraction Errors and Interruptions

- **Check Name:** Extraction Error and Interruption Check
- **Target:** Python extraction execution, database queries, connection status, and extraction logs.
- **Purpose:** To detect failed queries, connection interruptions, timeouts, or premature termination that may prevent the complete retrieval of source records.
- **Validation Criteria:**
  - **Pass:** All required extraction operations complete successfully, and no unresolved errors or interruptions affect the completeness of the extracted dataset.
  - **Fail:** A required query fails, the extraction process terminates prematurely, or an unresolved connection interruption prevents the complete retrieval of the required records.

## 4. Extraction Metadata and Log Specification

| Field Name | Purpose | Value |
|------------|---------|-------|
| `pipeline_run_id` | Uniquely identifies each extraction run. | `Run_20261013_001` |
| `table_name` | Identifies the source table being extracted. | `transactions`, `inventory`, `customer_traffic` |
| `extraction_start_timestamp` | Records when extraction begins. | `2026-10-13 23:00:00` |
| `extraction_end_timestamp` | Records when extraction finishes. | `2026-10-13 23:00:15` |
| `extraction_status` | Indicates whether extraction succeeded or failed. | `SUCCESS` / `FAILED` / `PARTIAL` |
| `records_read` | Records the number of source records examined. | `1250` |
| `records_extracted` | Records the number of records successfully retrieved. | `1250` |
| `records_rejected` | Counts records rejected due to data-quality issues. | `5` |
| `extraction_window` | Specifies the date or time range covered by extraction. | `2026-10-12 00:00:00 to 23:59:59` |
| `validation_results` | Records whether the applicable validation checks passed or failed. | `PASS` / `FAIL` |
| `error_message` | Describes the problem encountered. | `Database connection timeout` |
| `error_code` | Identifies the error using a code. | `DB_CONNECTION_TIMEOUT` |
| `extraction_duration` | Records the total time required for extraction. | `15 seconds` |

### 4.1 Monitoring

The extraction start and end timestamps, extraction status, record counts, and extraction duration will be used to monitor the daily batch process. These fields will help determine whether extraction runs as scheduled and whether unusual delays or unexpected record counts occur.

### 4.2 Troubleshooting

The validation results, rejected record count, error messages, and error codes will help identify problems such as database connection failures, incomplete extraction, or invalid data. These details will guide the investigation and correction of errors.

### 4.3 Auditing

The pipeline run ID, source table name, timestamps, extraction window, and record counts will provide a traceable record of each extraction run. These records will help verify what data was extracted, when extraction occurred, and whether the required validation checks were completed.

### 4.4 Recovery

The extraction status, extraction window, record counts, and error details will help identify failed or incomplete runs and determine which data needs to be extracted again. After the underlying issue is resolved, the affected extraction can be rerun, with checks to prevent duplicate records and ensure data completeness.

## 5. Log Retention and Access

| Requirement | Specification | Justification |
|-------------|---------------|---------------|
| Log retention period | Retain operational extraction logs for at least 90 days. Retain audit records for 1 year, subject to institutional requirements. | The proposed periods provide time to investigate extraction failures, compare previous runs, verify ETL activities, and support audits. |
| Storage location | Store extraction logs in a dedicated ETL log table in the PostgreSQL data warehouse or in a designated log file location accessible to authorized personnel. | Centralized and organized storage makes extraction records easier to retrieve, review, and manage. |
| Access permissions | Restrict access to authorized personnel responsible for maintaining and monitoring the ETL pipeline. Grant read-only access to personnel who only need to review logs. | Access restrictions help protect log integrity and prevent unauthorized viewing, modification, or deletion. |
| Archiving requirements | Archive audit records and other logs that must be retained beyond the operational retention period in secure storage. | Archiving preserves important extraction records while keeping active logs manageable. |
| Deletion rules | Delete or purge logs only after their applicable retention period has expired and they are no longer needed for troubleshooting, auditing, recovery, or an ongoing investigation. | This prevents the premature loss of records required to investigate failures or verify previous extraction activities. |
| Responsible process | Assign the ETL administrator or designated system maintainer to oversee log retention, archiving, access permissions, and authorized deletion. | Assigning responsibility helps ensure that log management procedures are applied consistently. |

The logs may be classified into two categories:

1. **Operational logs:** These logs record routine ETL activities, including pipeline run IDs, extraction timestamps, extraction status, record counts, validation results, execution duration, and error messages. They will be retained for at least 90 days to support daily monitoring, troubleshooting, and recovery.
2. **Audit records:** These records provide a history of extraction activities, including when a process ran, which source table was processed, the extraction window, the results of validation checks, and whether the process succeeded or failed. They will be retained for one year under the proposed policy, or longer if required by institutional policies or ongoing investigations.

### 6.2 Naming Convention

The following naming conventions are proposed to maintain consistency throughout the ETL pipeline.

| Element | Naming Convention | Example |
|---------|-------------------|---------|
| Table names | Use lowercase snake_case. | `fact_sales_summary` |
| Column names | Use lowercase snake_case with descriptive names. | `total_orders` |
| Primary keys | Use the table's identifying name followed by `_key`, consistent with the documented warehouse schema. | `sales_summary_key` |
| Foreign keys | Use the referenced key's name. | `date_key` |
| Date and time fields | Use descriptive names that indicate the stored value. | `full_date`, `peak_hour` |
| Abbreviations | Avoid unclear abbreviations; use full descriptive words where practical. | `customer_id` instead of `cust_id` |
| Numeric fields | Use names that describe the measure being stored. | `total_sales`, `low_stock_items` |

### 6.3 Schema Consistency

Unexpected changes to source column names, data types, or required fields must be checked against the documented data contract. If a source column name changes, the corresponding mapping must be updated while maintaining a consistent standardized column name. If a data type changes, the mapping must specify the appropriate target type. If a required field is missing, the issue must be flagged and resolved before the affected data is processed.

## 7. Extraction Acceptance and Handover Rules

### Decision Rules

| Validation Condition | Acceptance Criteria | Pipeline Action | Decision Type | Responsible Person or Role |
|----------------------|---------------------|-----------------|---------------|----------------------------|
| All required records are extracted successfully, and critical validation checks pass. | APPROVED | Proceed to Transformation | Automatic | Not required |
| Non-critical warnings are detected, such as unexpected record counts. | MANUAL REVIEW | Hold pipeline until reviewed | Manual | Person responsible for the ETL pipeline |
| A critical validation check fails or the source database is unavailable. | REJECTED | Retry extraction for temporary connection failures. If validation still fails, stop the pipeline and hold the extracted data from further processing. | Automatic | Person responsible for the ETL pipeline, if manual intervention is required |

### Validation Summary

| Validation Check | Expected Result |
|------------------|-----------------|
| Sales records extraction | PASS |
| Inventory records extraction | PASS |
| Customer traffic records extraction | PASS |
| Overall Extraction | APPROVED if all critical validation checks pass |

When extraction is approved, the extracted records from the sales, inventory, and customer traffic data are passed to the transformation stage. The handover includes the extracted data, processing date, extraction status, and validation results to support the subsequent cleaning, filtering, joining, and aggregation of records.

If manual review is required, the pipeline remains on hold until a decision is made. Rejected data must not proceed to transformation.

## 8. Common Extraction Problems and Mitigation

The following are common extraction problems that may occur when retrieving sales, inventory, and customer traffic records from the Jowen Two Three operational database.

| Problem Description | Possible Cause | Impact on Extraction | Proposed Solution or Mitigation |
|---------------------|----------------|----------------------|---------------------------------|
| Source Database Connection Failure | The Supabase PostgreSQL database is unavailable, or the database connection settings are incorrect. | Python cannot retrieve the required operational records, preventing the batch extraction from completing. | Check the database connection settings and source database availability, then retry the extraction. |
| Incomplete Data Extraction | Some required records are not retrieved during the scheduled batch process because of an interrupted connection or an incomplete query. | The extracted dataset may omit sales, inventory, or customer traffic records needed for reporting. | Verify the extraction results and record counts against the source query. Retry extraction if the results are incomplete. |
| Missing or Invalid Field Values | Some operational records contain missing values or values that do not match the expected data types. | The extracted records may fail validation or cause problems during the subsequent cleaning and transformation stages. | Validate required fields and data types after extraction. Flag invalid records for review before transformation. |
| Duplicate Records | The extraction process retrieves the same operational records more than once during a batch run or retry. | Duplicate records may lead to inaccurate sales totals, inventory summaries, or customer traffic counts. | Check for duplicate records using the appropriate record identifiers before passing the extracted data to transformation. |
| Unexpected Record Counts | The number of extracted records differs from the expected number for the processing date. | The extraction may be incomplete or may contain unexpected records, affecting the accuracy of subsequent reports. | Compare extracted record counts with the corresponding source query results and review discrepancies before proceeding. |
